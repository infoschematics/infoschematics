# An unrecapturable baseline

## Goal

A checked-in baseline can be regenerated by the repository that holds it, or the repository says who can regenerate it and how.

## Context

`scripts/fixtures/ibc-2026-visual-baseline.json` is a rendered visual baseline, and `scripts/ibc-visual-compatibility.ts` is the instrument that captures and compares against it. Nothing in this repository can produce it.

Two reasons, both verified on 2026-09-26. The `capture` and `compare` verbs exist only in the file's own usage text at lines 64 and 65; no `package.json` script and no Turborepo task invokes either, so the only thing that reads the module in the gate is `scripts/ibc-visual-compatibility.test.ts`, which compares two manifests handed to it and never renders anything. And `loadSharp` at line 294 walks upward from the directory given as `--fixture` looking for `node_modules/sharp`, which means it expects to be pointed at an external IBC workspace that depends on `sharp`; this repository depends on it nowhere.

So the baseline is external-fixture evidence living in this repository's fixtures directory, indistinguishable at a glance from the fixtures a suite here actually regenerates. [INFOSCHEMATICS-TOOL-129](INFOSCHEMATICS-TOOL-129-mode-style-and-hue.md) predicted in its `## Verify` that a change to every palette in the product would move this baseline and that the movement should be reviewed. It did not move, and nothing that change could have done would have moved it — the prediction was reasonable from the file's name and location and wrong about what the file is.

## Boundary

What the repository says and can do about this one baseline and its instrument. The decision is which of three it is: a genuine cross-repository check that needs its invocation and its external prerequisite documented where a reader of the fixture will find them; a check that belongs in the IBC repository rather than this one, in which case it hands over per the cross-repository rule in the harness workflow; or evidence of a comparison already made and finished, in which case it is a record rather than a baseline and should stop looking like something a gate maintains.

It does not decide whether visual compatibility with IBC still matters as a product concern, and it does not add `sharp` to this repository to make the capture work locally — that would be answering the question by making the repository carry a native image dependency it has so far avoided, which is a trade worth naming rather than falling into.

## Discussion

Found on 2026-09-25 while delivering [INFOSCHEMATICS-TOOL-129](INFOSCHEMATICS-TOOL-129-mode-style-and-hue.md), whose record instructed a recapture that turned out to be unperformable. Captured rather than repaired inside that item, because the item's boundary was the colour model and this is a question about a verification instrument.

Worth doing for the same reason as the "a check that measures nothing reports success" rule in `AGENTS.md`, arriving from the other side: this check does measure something, but nobody here can make it measure again, and a baseline that cannot be regenerated cannot be reviewed when it ought to move. The cost of leaving it is that the next person to change rendering reads the same filename, makes the same prediction, and spends the same time discovering the same thing.
