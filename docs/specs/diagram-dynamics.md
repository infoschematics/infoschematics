# Diagram Dynamics — DYNAMIC

Named authored Dynamics, host-owned occurrences, occurrence resolution, and non-motion interpretations. Part of the [Specifications corpus](index.md).

Flow signal occurrences themselves are specified in [Flow signals](flow-signals.md); this area specifies the authored vocabulary a host binds and how an occurrence of it reaches each renderer.

## User-observable behaviours

### DYNAMIC-001 — A Diagram declares the Dynamics it can express

A Diagram MAY declare named Diagram Dynamics under `diagram.dynamics`. Each declaration MUST carry a stable authored `id`, a human `label`, an optional `description`, and one `kind` from the finite vocabulary `signal-flow` or `emphasise-elements`. A `signal-flow` declaration MUST name one or more authored Flows; an `emphasise-elements` declaration MUST name one or more authored visual elements.

An `emphasise-elements` declaration MAY carry `depicts` with the value `event` or `state`, saying whether the change it names is something that happened or something that is now the case. An absent `depicts` MUST read as `event`, so a document written before the field existed keeps its meaning. Validation MUST reject `depicts` on a `signal-flow` declaration, whose occurrence is a passage along a Flow and has nothing to sustain. The vocabulary of kinds MUST stay finite at `signal-flow` and `emphasise-elements`: a depiction says more about what the Dynamic means, and MUST NOT be a second way of saying how it is drawn.

Validation MUST reject a duplicate Dynamic id, an empty target list, an unknown target identifier, and a target field belonging to another kind. Canonicalisation MUST retain authored declaration order and MUST store each target list sorted, so an authored reordering of targets does not change the canonical model.

A declaration MUST NOT carry a duration, easing, colour, selector, callback, timer, renderer component, event-source description, or any other rendering or runtime instruction. `depicts` is bound by the same rule: it fixes no duration, no treatment, and no way of playing, and a renderer that cannot sustain anything MUST still be able to honour it. A document that declares no Dynamics MUST validate, serialise, and render exactly as it did before the vocabulary existed: the collection MUST be absent from compact serialisation and MUST leave every renderer's output unchanged.

_Conformance:_ conforming

_Verify:_ Run `bun run test --filter=@infoschematics/domain-core` and `bun run self:schema:verify`, then author the declarations that must be refused and confirm each is: a duplicate Dynamic id, an empty target list, an unknown target identifier, a target field belonging to the other kind, and `depicts` on a `signal-flow` declaration. Canonicalise one document twice with its target lists reordered between runs and diff the results — the target lists must come out sorted and identical while the authored declaration order stands. Omit `depicts` from an emphasis declaration and confirm it reads as `event`, and confirm no declaration accepts a duration, easing, colour, selector, callback, timer, or renderer key. The refusals are written in `packages/domain-core/src/model.ts` and reach the generated schema through `packages/domain-core/src/schema.ts`, and the sorted target lists come out of `packages/domain-core/src/serialise.ts`.

_Evidence:_ canonical Dynamic types in `packages/domain-model/src/model.ts`, with duplicate, empty, unknown-target, and wrong-kind rejection and empty-collection serialisation covered by `packages/domain-core/src/model.test.ts`, `packages/domain-core/src/authoring.test.ts`, and the generated `packages/domain-core/schema/infoschematic.schema.json`; a retained `depicts` on an emphasis declaration, its rejection on `signal-flow`, and its authored round trip in `packages/domain-core/src/model.test.ts` and `packages/domain-core/src/authoring.test.ts`.

### DYNAMIC-002 — A host says only that a named Dynamic happened

A View or renderer boundary MUST accept framework-neutral `DynamicOccurrence` values carrying one `dynamicId` and one host-owned `occurrenceKey`. Retaining the same pair across renders MUST NOT restart a completed occurrence; supplying a new occurrence key for the same Dynamic MUST permit replay. Withdrawing an occurrence MUST cancel it.

An occurrence of a Dynamic that depicts a state MUST last as long as the host holds it: no renderer timer may retire it, and it MUST end only when the host withdraws it, replaces its occurrence key, or the elements it names stop being drawn. An occurrence of a Dynamic that depicts an event MUST continue to retire on its own, so the finite reading is what a document gets by saying nothing.

An occurrence naming a Dynamic the document does not declare MUST be ignored without diagnostics, output change, or instability. A repeated occurrence of the same Dynamic and key in one submission MUST resolve once.

Occurrences, keys, and any timers a renderer uses MUST remain host or View state and MUST NOT enter the authored Infoschematic or process-global state. Filtering, hover, focus, selection, and ordinary re-rendering MUST NOT synthesize occurrences.

An occurrence MAY originate from a Scene cue as well as from a host: a Scene naming a Dynamic (`SCENE-007`) is the document asking for that change while the Scene holds, and the View presenting the Scene owns the key and any cadence. Both sources MUST reach a renderer as occurrences of the same kind, a renderer MUST NOT distinguish them, and a host occurrence and a cued one MUST play together rather than either suppressing the other.

_Conformance:_ conforming

_Verify:_ Run `bun run test --filter=@infoschematics/view-canvas` and `bun run test --filter=@infoschematics/view-present`, then drive the occurrence boundary by hand: hold the same `dynamicId` and `occurrenceKey` across renders and a completed occurrence must not restart; change only the key and it must replay; withdraw it and it must cancel. Hold an occurrence whose Dynamic depicts a state and watch past the finite duration — it must still stand until the host withdraws it. Submit the same Dynamic and key twice in one submission and confirm it resolves once; name an undeclared Dynamic and confirm silence rather than a diagnostic, an output change, or a wobble; then filter, hover, focus, select, and re-render and confirm no occurrence was synthesized. The occurrence contract that answers all of this is `packages/view-model/src/dynamics.ts`, and the retirement effect sits in `packages/view-canvas/src/Canvas.tsx`. Then present a Sequence whose Scene cues one Dynamic while the host supplies an occurrence of another, and confirm both are drawn, that the cued occurrence ends with its Scene, and that the host occurrence survives Scene steering untouched. Falsified by a cued occurrence a renderer can tell apart from a host one, or by either source suppressing the other.

_Evidence:_ occurrence resolution, deduplication, and unknown-Dynamic tests in `packages/view-model/src/dynamics.test.ts`; replay, hold, and cancellation across the Canvas boundary in `packages/view-canvas/src/Canvas.dynamics.test.tsx` and `packages/view-canvas/src/Canvas.dynamics.browser.test.tsx`, where a held occurrence is watched outliving the finite duration and then ended by the host withdrawing it; pass-through of a held occurrence in `packages/view-present/src/Present.dynamics.test.tsx`. ### DYNAMIC-003 — Resolution reaches only what a renderer drew

View Model MUST resolve an occurrence against its declaration into renderer-facing Flow signals for `signal-flow` and element emphasis for `emphasise-elements`. A resolved Flow signal MUST be indistinguishable from one a host supplied directly through the `signals` boundary, so a Dynamic MUST NOT acquire a lifecycle that a directly supplied signal does not have.

Element emphasis MUST be applied only to elements the renderer actually drew. An occurrence MUST NOT reveal, unhide, or reposition content that Scope filtering, Scene focus, or output-detail policy excluded, and MUST NOT change authored geometry, routing, hit targets, selection behaviour, or any element's own output. A treatment MAY redraw, in its own layer and its own paint, a decoration the element already draws — a Flow's arrowhead, say — so that an emphasised element reads as one emphasised thing rather than an emphasised line ending in an unemphasised point. That is a decoration the occurrence owns and withdraws with itself: the element's own output MUST be unchanged underneath it, and MUST be what remains when the occurrence retires.

Resolution MUST carry a declared state depiction onto every emphasis it resolves from that declaration, and MUST leave an event's resolved emphasis exactly as it resolved before depiction existed, with no depiction field present at all — absence is the reading, not a recorded default.

Resolution MUST remain pure and framework-neutral: no renderer reads authored Dynamic shorthand, and each renderer chooses its own treatment from the resolved occurrences.

Where a treatment needs geometry more specific than a box — a line a mark can be seen to travel rather than a rectangle to outline — that calculation MUST live in View Model and MUST be the single calculation every renderer draws from, so two renderers cannot disagree about where an element's perimeter runs. The calculation MUST answer only where the perimeter is: it MUST NOT state what is drawn on it, which way round it is travelled, or where anything rests along it, all of which stay renderer choices.

Resolution MUST NOT say which geometries a treatment is offered for. A renderer MAY decline a treatment for an element whose geometry cannot carry it legibly, and MUST then draw that element the treatment it can carry rather than nothing, so an element a Dynamic names is never left unmarked. Which geometries a renderer declines, and at what cost to the reader, MUST be recorded in [ADR-INFOSCHEMATICS-027](../decisions/ADR-INFOSCHEMATICS-027-author-what-an-emphasis-means-not-how-it-is-played.md) rather than discovered from the output.

_Conformance:_ conforming

_Verify:_ Run `bun run test --filter=@infoschematics/view-model`, `bun run test --filter=@infoschematics/view-canvas`, and `bun run test --filter=@infoschematics/render-svg`, then occur a Dynamic whose targets are hidden by Scope filtering, excluded by Scene focus, and dropped by output-detail policy in turn: each render must be byte-identical to the quiet one. With a drawn target, diff the element's own output between quiet and occurring — authored geometry, routing, hit targets, and selection behaviour must be untouched, any decoration the treatment adds must sit in its own layer, and it must be gone when the occurrence retires. Confirm a resolved Flow signal is indistinguishable from one a host supplied through the `signals` boundary, and that a declared state depiction reaches every emphasis resolved from that declaration while an event's resolved emphasis is exactly as it was. `resolveDiagramDynamics` and `dynamicDepictsState` in `packages/view-model/src/dynamics.ts` are what resolve this, the shared perimeter comes from `packages/view-model/src/perimeter.ts`, and the emphasis layers to diff are drawn by `packages/view-canvas/src/InfoschematicDiagram.tsx` and `packages/render-svg/src/index.ts`.

_Evidence:_ byte-identical resolved and directly supplied signal output, scope-hidden elements left unemphasised, and unchanged element output in `packages/view-canvas/src/Canvas.dynamics.test.tsx`, `packages/view-present/src/Present.dynamics.test.tsx`, and `packages/render-svg/src/index.test.ts`; the closed, clockwise, radius-fitted perimeter and its outset in `packages/view-model/src/perimeter.test.ts`, both renderers drawing that same perimeter for the same box in `scripts/visual-treatment-parity.test.ts`, and a travelling treatment offered where a closed perimeter exists while a Flow keeps its route outline and a Point its disc in `packages/view-canvas/src/Canvas.dynamics.test.tsx`.

### DYNAMIC-004 — Static output stays quiet unless a caller asks

Deterministic still output MUST be byte-identical with no declared Dynamics, with an empty occurrence list, and with an occurrence naming an undeclared Dynamic. A caller MAY supply occurrences explicitly, and the renderer MUST then draw its still treatment for the resolved targets.

Still output MUST NOT distinguish a state from an event: one image has no duration to express, so a held occurrence and a momentary one draw the same outline. A caller that needs to show what is currently the case does so by supplying the occurrence.

Nor MUST still output distinguish a travelling treatment from a finite one. A single frame has no time in which to travel, and the direction a mark traces is a renderer's choice made from the geometry rather than anything the document states, so there is no authored direction for a still frame to record and it MUST NOT invent one: a frozen mark or a start marker would show a reader a movement the document never asserts. Where an interactive renderer sends a mark along an element's perimeter, still output MUST draw that same perimeter as its outline and nothing travelling on it.

Still output MUST NOT contain animation, and MUST NOT vary with the occurrence key: two occurrences of the same Dynamic differing only by key MUST produce identical output. Emphasised elements MUST carry stable authored artefact identity together with the Dynamic id so a caller can locate the treatment, and the accessible description MUST state the occurred Dynamics' labels.

_Conformance:_ conforming

_Verify:_ Run `bun run test --filter=@infoschematics/render-svg`, then render one document three ways — no declared Dynamics, an empty occurrence list, and an occurrence naming an undeclared Dynamic — and diff the bytes: all three must match. Supply an occurrence explicitly and confirm the still treatment is drawn for the resolved targets; then confirm a held occurrence and a momentary one draw the same outline, that two occurrences differing only by key produce identical bytes, and that the output contains no animation element and no start marker or frozen mark on an emphasis perimeter, either of which would show a reader a movement the document never asserts. Confirm each emphasised element carries its authored artefact identity alongside the Dynamic id, and that the accessible description states the occurred Dynamics' labels. The still treatment and the accessible description are both drawn by `packages/render-svg/src/index.ts`.

_Evidence:_ quiet-baseline, explicit-occurrence, key-independence, and accessible-description tests in `packages/render-svg/src/index.test.ts`, where the emphasis outline is asserted to be the shared perimeter calculation and the output to contain no travelling markup at all.

### DYNAMIC-005 — A Producer can rehearse a document's Dynamics

Studio MUST offer a Producer one control per declared Dynamic while presenting, and MUST NOT offer the bank for a document that declares none. Activating a control MUST play that Dynamic exactly as a host binding its id would, through the same occurrence boundary and with a key that changes on each activation.

A control for a Dynamic that depicts a state MUST hold: activating it MUST start an occurrence that stands until the Producer activates the same control again, which MUST withdraw it. A control for a Dynamic that depicts an event MUST keep playing a momentary occurrence that retires itself. Either way the control MUST report whether its Dynamic is currently occurring.

Rehearsal MUST NOT write to the authored document, MUST NOT persist across sessions, and MUST NOT change any Producer selection, mode, or editing state.

_Conformance:_ conforming

_Verify:_ Run `bun run test:browser --filter=@infoschematics/view-studio`, then present a document that declares Dynamics and one that declares none: the bank must appear only for the first, with one control per declaration. Activate a control and confirm the occurrence arrives through the same boundary a host binding that id would use, with a key that differs on each activation. Activate a state-depicting control and confirm it holds until activated again, which withdraws it; activate an event-depicting one and confirm it retires itself; both must report whether their Dynamic is occurring. Then diff the authored document and the Producer's selection, mode, and editing state across the rehearsal, and reload to confirm nothing persisted. The bank is `packages/view-studio/src/app/panels/ProducerControls.tsx` and its occurrence handling sits in `packages/view-studio/src/app/App.tsx`.

_Evidence:_ rendered Studio rehearsal, replay, and retirement in `packages/view-studio/src/app/App.browser.test.tsx`, where a state-depicting control is also watched holding past the finite duration and ending only on a second activation, and the hosted bank in `apps/site/src/Playground.test.tsx`.

## Quality properties

### DYNAMIC-006 — Every Dynamic means something without motion

Each kind MUST have a full-motion treatment, a finite `prefers-reduced-motion` treatment that is still rather than travelling, and a deterministic non-motion interpretation in still output. Motion MUST NOT be the only carrier of a Dynamic's meaning.

A full-motion treatment MAY send a mark travelling round an element. When it does, the mark MUST travel the very path the outline is drawn from, so it cannot cut a corner the outline rounds, and MUST complete its circuit in the same View Model token period the finite treatment takes. A mark travelling for a state MUST keep going for as long as the host holds the occurrence; one travelling for an event MUST make a single circuit. A travelling mark MUST NOT obscure an element's own text, and MUST NOT receive pointer events at any point on its circuit, so an element beneath the line it travels stays selectable throughout.

A travelling treatment carried by declarative SVG motion rather than by a CSS animation MUST be removed under `prefers-reduced-motion` rather than stilled, because no CSS animation property reaches it and a treatment that only appears to be switched off would keep moving. The steady outline MUST remain as the whole treatment, which is the picture still output already draws. Because a media query adds no specificity, every reduced-motion rule MUST be restated for each selector the full-motion treatment states, including the more specific sustained one, and MUST be held there by an assertion rather than by inspection. That assertion MUST be made of a page that answers `prefers-reduced-motion: reduce` for real rather than of the stylesheet text, because a restatement that loses on specificity is present in the text and absent from the treatment the browser resolved.

A sustained treatment for a state MUST be painted at every moment of the hold, never reaching full transparency, and MUST take its period from the same View Model token as the finite treatment. Under `prefers-reduced-motion` a hold MUST be steady rather than sustained, which is the outline still output already draws.

An interactive renderer MUST announce each newly accepted occurrence once through a concise polite live region, and the announcement MUST state the Dynamic's own label rather than describing the graphic or listing the elements it touched. Re-rendering the same occurrence MUST NOT repeat the announcement; cancelling or completing an occurrence MUST NOT announce new activity, so a hold is announced when it begins and its ending is silent — a reader who must know that a state has ended is told by the host, through whatever the host uses to say so. However many elements one occurrence touches, it MUST be announced once.

The obligation MUST fall on every host that mounts the interactive Diagram, not only on the Canvas that composes one. The announcement surface MUST be shared rather than restated per host, so a host that draws a Diagram mounts it and a host that resolves its own occurrences supplies them to it. A host MUST NOT mount two surfaces reporting one occurrence, and the Diagram itself MUST NOT carry the live region, because it renders an `<svg>` root a status paragraph cannot live in, as `ADR-INFOSCHEMATICS-029` records.

An announcement MUST be conditional on something having been drawn. Where visibility filtering removes every element an accepted occurrence would have been drawn on, the live region MUST stay silent: the revision counter MUST NOT be read without the sentence it distinguishes, because on its own it reports that something happened and withholds what. The rule MUST hold for every announcement path rather than for the paths that exist, so a host that filters what the Diagram draws MUST tell the shared announcement surface what was drawn — a host whose accepted set is already its drawn set needs to say nothing, and one that filters cannot be inferred about after the fact. `COMPOSE-004` in [Composition](composition.md) owns the composed case.

Emphasis graphics MUST be hidden from assistive technology and MUST NOT receive pointer events. Measurements shared between motion and still treatments MUST come from View Model visual tokens.

_Conformance:_ conforming

_Verify:_ Run `bun run test --filter=@infoschematics/view-canvas` and `bun run test:browser --filter=@infoschematics/view-canvas`, then watch each kind at full motion, under a page emulating `prefers-reduced-motion: reduce`, and in still output. Sample a travelling mark's position around its circuit and confirm it is on the outline's own path rather than cutting a rounded corner, that it completes in the same View Model token period the finite treatment takes, that a state keeps it going while the hold lasts and an event gets one circuit, that it covers no text, and that an element beneath it still takes a press at every sampled point. Sample a sustained hold part way through and confirm it is painted and has not reached full transparency. Under reduced motion, confirm the treatment carried by declarative SVG motion is removed rather than stilled and that the steady outline is the whole of what remains — measured from the resolved treatment in an emulating page, never from the stylesheet text, because a restatement that loses on specificity is present in the text and absent from the render. Listen to the live region: one announcement per newly accepted occurrence, stating the Dynamic's label however many elements it touched, with nothing on re-render, cancellation, or completion. Then rehearse one Dynamic in Studio, which mounts the Diagram without a Canvas, and confirm it is announced there too; delete the `DiagramAnnouncements` mount from `packages/view-studio/src/app/App.tsx` and the Studio case MUST fail, so a suite that only exercises Canvas is not read as covering every host. Confirm the emphasis graphics take no pointer events and are hidden from assistive technology. The circuit period comes from the emphasis tokens in `packages/view-model/src/tokens.ts`, the live regions from `packages/view-canvas/src/announcements.tsx`, and the reduced-motion emulation the browser suites ask for from `scripts/vitest-workspace.ts`. Then switch off every Flow family and Scope an occurrence touches and rehearse it again: the live region MUST be empty, with no revision counter left in it. Restore the counter unconditionally and that case MUST fail, so an empty region is read as the filter being obeyed rather than as nothing having been rehearsed.
