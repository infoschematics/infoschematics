# ADR-INFOSCHEMATICS-037: A palette belongs to a colour scheme, not an outlet

## Context

Until now the drawing's colours were chosen by the outlet that drew them. The token manifest said so in as many words — the interactive surface was dark, the static renderer's paper was light — and the tokens followed: `canvas.surfaces.backdrop` was `#081725` while `canvas.output.backdrop` was `#ffffff`, and `canvas.artwork` carried two complete ink groups so a piece of standard artwork could be painted either way.

That agreement was coherent while the question was "which renderer is this". It stops being coherent the moment the question is "what does the reader prefer", because the reader's preference is not a property of the renderer. [PDR-INFOSCHEMATICS-001](PDR-INFOSCHEMATICS-001-an-infoschematic-is-an-authored-definition-not-a-drawing.md) positions an [Infoschematic](../reference/vocabulary.md#infoschematic) as an input embedded where it is read — in a document, a site, a build pipeline. A definition that can only be drawn dark cannot honour that: embedded in a light document it is a black rectangle in the middle of the page, and an SVG committed to a repository is wrong for half the people who open it.

Nothing in the repository read `prefers-color-scheme` at all, in any TypeScript, stylesheet, document or manifest. So the decision was not how to add a second palette to an existing scheme mechanism; it was whether a scheme exists as a concept here, and who gets to resolve it.

Three questions had to be settled together: what a palette is attached to, who decides which one applies, and what a file that nobody will ever ask does.

## Decision

A palette belongs to a **ground**, and a ground is one of two things a drawing is painted from. The other is a **style**. One role set — 36 paint roles plus the standard-artwork inks — is realised by four palettes, one for each pairing of `neutral` or `blueprint` with `light` or `dark`. Every palette answers every role, or the generated stylesheet is not written; a role one palette declares and another does not would resolve to whatever an earlier block left behind, and the drawing would be half in one palette under a preference no default page expresses.

**The browser resolves the scheme for an interactive drawing.** Canvas references a role as its own custom property rather than resolving a palette in TypeScript, because the reader's preference and a host's override are both things the browser already knows and a module does not. The generated stylesheet declares `light` on `:root`, `dark` behind `prefers-color-scheme` and again behind `[data-infoschematic-scheme]`, so the default path needs no script at all and a host that has resolved the scheme itself can say so. This keeps [ADR-INFOSCHEMATICS-005](ADR-INFOSCHEMATICS-005-host-owned-configuration.md) intact: reading a URL parameter, storing a choice and listening to the operating system stay the host's work, and what reaches a package is a resolved answer or nothing.

**A still rendering resolves the scheme once and writes the colours it settled on** — because nothing downstream of it can react. A caller who wants both renders twice, which is also what makes the two comparable.

**A rendering may also decline to choose.** `scheme: 'adaptive'` writes one SVG carrying both palettes in its own `<style>` element behind `prefers-color-scheme`, scoped to the drawing's own element rather than `:root` so the same markup inlines into a page without declaring a palette over everything around it. This is the form our output most often takes in somebody else's repository, read by people whose preference we will never know. A raster cannot take it: the colour is in the pixel, so [ADR-INFOSCHEMATICS-022](ADR-INFOSCHEMATICS-022-rasterise-with-a-native-resvg-binding.md)'s encoder has to be told, and `--scheme adaptive --format png` is refused rather than quietly resolved.

An adaptive rendering references its roles through inline `style` rather than presentation attributes. `fill="var(--paint)"` is a CSS value only where SVG 2's presentation-attribute parsing is implemented — it resolves in Chromium — and a file committed for strangers to open is exactly the output that cannot depend on which engine they use.

What an adaptive rendering does depend on is a consumer that resolves custom properties, and no fallback rescues one that does not. resvg reads an inline `style` and then treats `var(...)` as an invalid paint: it paints black, and looks past both a `var()` fallback and the presentation attribute beneath it. So the choice is between a drawing that follows its reader and one that any consumer can read, and it is the caller's: `adaptive` is for embedding where CSS applies, and anything else asks for a resolved scheme.

**Paper is a light ground whatever the screen was.** Both palette carriers — the generated stylesheet and an adaptive SVG's own `<style>` — end with a `print` rule restoring the light ground. It shares `:root`'s specificity with the reader's preference and the host's override, so it is source order that makes it win, which is why the claim is held by a browser case asking the page for `print` rather than by reading the stylesheet. An authored blueprint prints in its own light realisation. That reverses what this record said first, and the reversal follows from the clause below: paper is a ground, a blueprint is a style, and a style laid onto paper without regard for the ground it is on is a navy rectangle on a white page. It is still a blueprint on paper — the cyanotype one.

**A style is authored, a ground is resolved, and they are orthogonal.** One enum was doing three jobs: it named a palette, it named a ground, and it named an authored treatment. So a document that chose `blueprint` could not follow its reader, and a reader's preference could not reach a document that had chosen anything. The two axes separate. A document authors `appearance.style` — `neutral` or `blueprint` — which says what the drawing _is_, per [ADR-INFOSCHEMATICS-011](ADR-INFOSCHEMATICS-011-separate-authored-appearance-from-output-detail.md). Whoever renders resolves the mode — `light` or `dark` — which says which ground the _reader_ is on. A document may state a preferred mode, and `system` is the author declining to pick rather than a third ground: it falls through to the caller, and then to `light`, because a still picture has no preference to read and an unresolved palette rasterises to nothing. The style lands on the drawing and the mode on the document element, so CSS specificity composes them instead of one overruling the other.

**An authored colour is a hue seed.** Pinning an author's colour kept its meaning for exactly as long as there was one ground. `#6c8ebf` chosen against navy is a different colour on paper, and the author is not in a position to meet both at once — they wrote one value. So the hue is theirs, the saturation is theirs, and the ordering between the colours they chose is theirs, while the lightness band that ordering is realised in belongs to the ground. An author who meant a literal value ends it with `!`: a suffix rather than a companion field, because every authored colour is already a string in a position that exists, and a parallel boolean beside each one would widen the contract in six places to say something about a value rather than about the thing carrying it. A value the rule cannot read — a named colour, a gradient reference — is passed through untouched, because refusing to interpret something is better than guessing at it.

A seed is realised for one of three jobs. `fill` and `ground` share a lightness band and differ only in translucency: a Region is a backdrop covering much of the drawing, so an opaque one erases the grid and every ruled line under it, while a Card is a body and an author who coloured one meant a coloured body. `ink` is the third — text, strokes and arrowheads, which have to carry against the ground rather than sit on it. Readable ink is then measured against the fill that was drawn rather than the one that was written, which is the only reading that stays legible once the fill itself moves with the ground.

The alternative was a closed vocabulary of roles an author could name — `accent`, `caution`, `muted` — resolved per ground. It was rejected because it takes away the thing the feature exists to give: an author picks a colour because they mean that colour, and a fixed list of six names is a different product from a colour field. The seed keeps the choice and moves only what the author could not have known, which is the ground their reader is on.

**A surface we host offers the switch; a drawing we embed does not.** The role model extends to chrome unchanged — one set of interface roles in `light` and `dark`, beside the paint roles and in the same manifest, because a second palette invented inside a stylesheet is precisely what left the chrome unswitchable the first time. What does not extend is the control. Studio and the website carry a scheme switch in the header each already has, because a reader of a surface we host has nowhere else to ask. An embedded Diagram carries none: it has no chrome to put one in, and ADR-INFOSCHEMATICS-005 gives the host the page. Present carries none either, and that is a decision rather than an omission — its controls belong to the presenter, and a reader's viewing preference is not a presentation control, so a presenter pins the scheme before starting and the Audience sees what the room needs. The three are not one promise: hosting a surface is undertaking to offer the choice, while embedding a drawing is undertaking only to honour whichever choice the page has already made.

There is no blueprint chrome. `blueprint` is an authored treatment of a drawing per ADR-INFOSCHEMATICS-011, so the blueprint selector redeclares paint roles only; the interface around a blueprint stays in the reader's own scheme, because the reader did not author the document they are reading.

## Consequences

The `output`, `surfaces` and `artwork.ink` token groups are gone. Every consumer now names a role and either resolves it for a scheme or references it as a custom property, and the standard-artwork catalogue of [ADR-INFOSCHEMATICS-031](ADR-INFOSCHEMATICS-031-the-product-offers-renderer-artwork-as-data.md) paints itself from the artwork roles rather than from one outlet's inks — one catalogue, correct in every scheme.

Renderer parity now compares the **role** each outlet names rather than the colour it wrote, because the two deliberately differ about resolution: Canvas emits `var(--infoschematic-canvas-paint-artwork-mark)` where the static renderer writes `#9cd5f58c`, and both are right. A parity check that compared literals would fail on a correct pair.

Three gates hold the role agreement, in the three places it can break: the generator refuses to write the stylesheet when the palettes disagree about which roles exist, the manifest suite asserts every role in every scheme, and a browser case asserts that each declared block resolves the same role names — which is the only place the half-painted failure is visible at all.

The command surface names a ground rather than a palette. `--mode` takes `light`, `dark` or `system`, and passing nothing passes nothing on, so a document that authored a mode keeps it rather than being overruled by a flag's default. `--scheme` keeps working as the retired spelling, with `adaptive` reading as `system` and `blueprint` — which named a palette under the old vocabulary and names a style under this one — accepted and treated as naming no ground at all.

The chrome around the drawing now resolves in both schemes too, which cost 520 raw colour literals across four stylesheets — 157 of them distinct — collapsing onto 36 interface roles. A check states a floor of zero literals in those files rather than counting what happens to be there, because the layer's failure mode is one copied rule that looks perfectly correct in whichever scheme it was picked in. `INFOSCHEMATICS-TOOL-118` delivered that half; the drawing reading correctly in light inside chrome that was still dark would have been a coherent half-delivery, and the reverse would not.

The document contract widens by three fields on `diagram.appearance`: `style`, `mode` and `modeLocked`. `surface` is retained as the retired spelling of `style` and loses to it where both are written, so nothing already authored stops loading. Both renderers resolve seeds at the point of use rather than ahead of the drawing, and a rendering that declines to pick a ground pools its seeds into custom properties declared once in each palette block — the same mechanism the manifest's own roles travel by, applied to values the document supplied.

The naming has not caught up with the model. `data-infoschematic-scheme`, `useColourScheme`, `colour-scheme.ts` and the stored preference key all still say `scheme` where they now mean a mode, across about thirty files. Only the attribute and class that named a style moved — `data-infoschematic-style` and `style-blueprint` — because those were the two the new selector arrangement had to get right. The rest is a rename with no behaviour in it and is deferred to its own record rather than folded into this one.

A blueprint now has a light realisation that did not exist before, and nothing here can tell anyone whether it reads as a blueprint. Its contrast ratios are measured and its roles are complete, which is what a suite can say; whether a cyanotype on paper is recognisably the same drafting convention as the navy one is a judgement only a person looking at it can make.
